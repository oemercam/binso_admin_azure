## Berechtigungen, Secrets und Einstellungen

UI-Lesezugriffe auf Repository Settings und Production-Environment ergänzten die API. Das administrative Branch-Protection-API gab 403 für die Integration zurück; das bedeutet keine fehlende Protection. Der sichtbare klassische Regelsatz verlangt PR, up-to-date Checks `quality` und `analyze` aus GitHub Actions sowie aufgelöste Gespräche. Force-Push und Branch-Löschung sind verboten, Admin-Umgehung der Branchregel deaktiviert. Keine erforderlichen Reviews, signierten Commits oder lineare Historie. Ruleset-Liste ist leer.

Actions-Standardtoken ist read-only für Contents/Packages; Actions dürfen PRs nicht erstellen/approven. Alle Actions sind im Source bereits SHA-gepinnt, obwohl die globale UI alle Actions zulässt und Pins nicht erzwingt. Fork-Freigabe gilt für Erstbeitragende, nicht pauschal alle externen Beitragenden. Quality hat keine OIDC-Berechtigung. CodeQL braucht ausschließlich im Analysejob `security-events: write`. Deploy braucht `actions: read` zum Lesen qualifizierter Runs/Artefakte und jobbezogen `id-token: write`; operative Azure-Jobs brauchen OIDC für ihre Anmeldung. `contents: write` ist für diese Workflows nicht erforderlich.

Environment-Secret-Namen: `AZURE_CLIENT_ID`, `AZURE_SUBSCRIPTION_ID`, `AZURE_TENANT_ID`, `BINSO_ONE_INTERNAL_JOB_SECRET`, `DATABASE_URL`. Repository enthält dieselben drei Azure-ID-Namen sowie drei alte `AZUREAPPSERVICE_*`-ID-Namen, die von den neun aktuellen Workflows nicht referenziert werden. `BINSO_ONE_BASE_URL` ist Environment-Variable. Nicht verwendete Namen sind zunächst Inventarbefunde, keine Freigabe zum Löschen. Kein Secret-Wert wurde geöffnet, kopiert oder in den Bericht geschrieben. Graph-/Stripe-Werte werden von ARM zur Laufzeit gelesen und nicht als Klartext geloggt.

OIDC verwendet laut UI und historischen Azure-Loginlogs die immutable Standard-Subjectform `repo:oemercam@202777456/binso_admin_azure@1379293391:environment:production`, Audience `api://AzureADTokenExchange`, Issuer `https://token.actions.githubusercontent.com`. Azure-Federation/RBAC wurde nicht live gelesen; eine veraltete Subjectform ohne IDs darf nicht als aktueller Beweis gelten. Environment-Kontext allein belegt keine Main-Bindung der Azure-Identität.

### Verbleibende Optimierungsmöglichkeiten

Quality-Concurrency unterdrückt ältere Läufe desselben PRs/Refs. Push ist nur auf Main, PR auf Main: Feature-Push plus PR erzeugen damit keinen doppelten automatischen Quality-Lauf. Main nach Merge wird absichtlich erneut geprüft: anderer Commit und Artefaktherkunft. Manuelle Full- und PR-Läufe sind unterschiedliche Events/Concurrency-Gruppen; unnötige manuelle Wiederholungen vermeiden. CodeQL auf PR/Main/zeitgesteuert bleibt als Sicherheitsabsicherung erhalten. Operative enge Pfadfilter liefern unabhängige Signals, ihr vollständiges Zusammenlegen würde Identity-/Failure-Isolation verlieren.

Backup liest dasselbe ARM-Serverobjekt dreimal: kleine mögliche Zusammenfassung, gemessener gesamter Job nur 24s; kein priorisierter Engpass. Graphs vier Settings-Reads wurden dagegen zusammengefasst, weil dort sensitive Datenhaltung und Schreibfreigabe ohnehin korrigiert werden mussten. Keine zusätzliche Beschleunigungsbehauptung ohne neuen Messlauf. Neue Hashprüfung hat bewusst zusätzlichen begrenzten Aufwand; deren Dauer wird im neuen Quality-Run sichtbar.

## Betriebsgrenzen und Wiederherstellung

`scripts/production-monitoring-check.sh` prüft Ressourcenanzahlen und Insights-ID, aber keinen vollständigen Alert-Scope, effektiven Empfänger oder End-to-End-Alarm. Backup-Readiness prüft Ready/Retention mindestens sieben Tage, meldet Geo-Backup, beweist aber keinen erfolgreichen PITR. Graph HTTP 202 beweist Annahme, nicht Zustellung. Stripe-GETs beweisen Konfiguration, nicht erfolgreiche Zahlung/Webhook-Zustellung. Keine dieser Grenzen rechtfertigt, einen Gatefehler zu ignorieren.

Deployment ist manuell und auf einen exakt qualifizierten aktuellen Main-SHA gebunden. Der erste neue Guard verhindert bereits vor Input-Checkout eine abweichende Ausführung. Der Resolver akzeptiert nur erfolgreichen `workflow_dispatch` auf `main`, `.github/workflows/quality.yml`, passenden SHA und Full-Profil; erfolgreiche PR-, Push- oder andere Workflow-Runs reichen nicht. Kandidat und Manifest werden gemeinsam heruntergeladen und vor Migration verifiziert, kein Rebuild während Promotion. Scanner-Qualifikation bleibt separat verifiziert. Artefakte sind derzeit zwei Tage verfügbar; Logs/Artefakte haben global 90 Tage Default, andere Evidenzartefakte eigene 7/14/30-Tage-Fristen, Cache sieben Tage/10 GB.

Bei einem Produktionsfehler müssen zuerst betroffene Settings, aktivierter Code-SHA und DB-Migrationsstand read-only festgestellt werden. Für Code ist ein geprüfter Forward-Fix auf Main mit neuem Full-Quality und explizitem Deploy der heute kompatible Weg. Datenbankschäden benötigen separaten freigegebenen Restore-/PITR-Plan und Kompatibilitätsprüfung; niemals automatisch Down-Migrationen ausführen. Slot-Swap, vorab validiertes Backup und unabhängiger Rollback-Artefaktpfad sind sinnvolle separate Architekturarbeiten, aber keine durch diesen Audit heimlich eingeführten produktiven Änderungen. Migrationsskript besitzt keine globale DB-Advisory-Lock-/Statementdeadline-Absicherung gegen außerhalb dieses Workflows parallel laufende Werkzeuge; Workflow-Concurrency allein löst das nicht.
