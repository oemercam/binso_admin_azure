# V82.0.6 Maintainability cleanup

Stand: 28.09.2026

## Ziel

Technische Schulden aus der gewachsenen V69–V82 Entwicklung reduzieren, ohne Funktionen, UI-Verhalten, Datenmodell oder bestehende API-Verträge zu ändern.

## Umgesetzt

- `app/app-ui.css` von rund 7'000 Zeilen auf einen stabilen Entry-Point reduziert und die bestehende Cascade in fünf geordnete Module aufgeteilt.
- Business Store in Provider/Commands, Typen, Tenant-State und reine Utilities getrennt.
- Normalisiertes Business-State-Repository in Persistenz, Laden, Shared-Mapping und Legacy-Bridge getrennt; der bestehende Importpfad bleibt als Facade kompatibel.
- Prüfskripte so angepasst, dass sie die modularen Quellen vollständig prüfen statt nur eine frühere Monolith-Datei.
- GitHub Actions auf `static:check` und `compatibility:check` konsolidiert. Historische Checks bleiben als Regression Contracts erhalten.
- Azure Edge-/Proxy-Trust und Access-Restriction-Anforderungen für IP-basiertes Rate Limiting dokumentiert.
- Wartungs- und Ownership-Regeln für die neuen Module dokumentiert.

## Bewusst unverändert

- UI/UX und bestehende visuelle Cascade.
- Business-Prozesse und Statusübergänge.
- Datenbankschema und Migrationen.
- API-Routen und öffentliche Verträge.
- Bestehende historische Regressionstests.

## Verifikation

Alle vorhandenen `scripts/check-*.mjs` laufen nach der Modularisierung erfolgreich. Ein vollständiger Projekt-Typecheck/Build benötigt die Projektdependencies und Node 24; die lokale Analyseumgebung enthält diese Dependencies nicht. Die verbindliche Endprüfung erfolgt daher mit `pnpm run release:check` auf Node 24 bzw. über GitHub Actions.
