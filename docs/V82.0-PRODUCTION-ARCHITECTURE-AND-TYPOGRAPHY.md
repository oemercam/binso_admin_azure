# V82.0 – Production architecture, hardening and typography

V82.0 is one consolidated implementation pass on top of V81.19.4. It deliberately follows an expand/strangler migration instead of replacing the working application in one uncontrolled rewrite.

## Normalized business persistence

The production state API now persists the main business collections into tenant-owned PostgreSQL rows and removes those collections from the compatibility JSON snapshot after a successful normalized write/backfill. Stable `external_id` values preserve the current UI identifiers while PostgreSQL keeps UUID primary keys.

Normalized collections:

- customers and customer contacts
- quotes and quote lines
- contracts and contract lines
- orders
- time entries
- invoices and invoice lines
- payments
- employees
- suppliers and supplier invoices
- expenses
- credit notes
- customer activities

The normalized schema includes tenant ownership, RLS, tenant-aware foreign keys, external IDs, revision counters, archive markers, useful list indexes and source links between invoices, time entries and expenses. Document numbers for customers, quotes, contracts, invoices and credit notes are allocated atomically in PostgreSQL.

`tenant_business_state` remains only for compatibility data that has not been normalized yet, for example UI workflow configuration and transient orchestration structures. BusinessStore may still coordinate the client UI, but the migrated collections are no longer written as the authoritative JSON business database after migration.

## Server-side integrity

The compatibility save path is still versioned and transaction-locked. V82 additionally verifies server-side:

- plan/feature and role write permissions
- deterministic quote/invoice totals using integer minor units
- quote, order and invoice status transitions
- customer/order/contract/source-quote relationships
- invoice source time entries and expenses
- approved/billable source requirements
- duplicate billing-source prevention within active invoices
- payment and credit-note totals against invoice amounts
- retry-safe business-state persistence through an idempotency key

Document sending reads canonical normalized rows after migration and updates normalized quote/invoice delivery state instead of depending on removed JSON arrays.

## Pagination and scale

`GET /api/business/records` provides tenant-authorized, bounded server-side pagination/search for customers, contacts, quotes, orders, time, invoices, payments, employees, contracts, suppliers, supplier invoices, expenses and credit notes. Default page size is 50 and maximum is 100.

The current UI remains on the controlled strangler path: not every page has been switched from BusinessStore view state to the paginated endpoint yet. This is intentionally left as a compatibility boundary rather than risking a full UI rewrite in the same database migration. New/large-list work should use the paginated endpoint and progressively retire full collection hydration.

A safe scale seed and read-only k6 scenario are included for local/staging validation.

## Backfill

The migration is additive. Apply the database migration first. Then dry-run the internal backfill before any write backfill.

`POST /api/internal/business-state-backfill` uses the existing internal bearer-secret authorization.

Safe default:

```json
{"dryRun":true}
```

Explicit write after review:

```json
{"dryRun":false}
```

A single tenant can be selected with `organizationId`. The backfill is designed to be repeatable because normalized writes use tenant/external-ID upserts and atomic document counters preserve already allocated numbers.

## Database roles

Application code already supports separate `DATABASE_URL` and `PLATFORM_DATABASE_URL` pools. Production should use separate least-privilege database users/roles. Creating/changing those Azure PostgreSQL credentials is an operator/infrastructure action and is intentionally not faked in application code.

Recommended separation:

- `DATABASE_URL`: tenant application role; tenant-scoped tables, RLS enforced
- `PLATFORM_DATABASE_URL`: explicitly authorized platform/operator workloads only
- migration credential: deployment-only DDL rights, not used by normal web requests

## Typography

Canonical typography tokens are owned by `app/styles/tokens.css`; selectors are mapped by `app/styles/typography-system.css`.

- Brand/public headings: Josefin Sans 500/600 through `next/font`
- Product/application/body/navigation/forms/tables: Inter 400/500/600/700 through `next/font`
- application roles: 24 / 16 / 14 / 13 / 12 px
- public H1: 34–52 px responsive
- public H2: 24–30 px responsive
- public H3: 18–20 px
- public body: 14–16 px
- mobile form inputs: 16 px
- business numeric surfaces: tabular numerals

The V82 typography layer also replaces many historical 8–10.5 px UI micro-sizes with the canonical 11–13 px small/caption hierarchy while preserving layout ownership and mobile/PWA behaviour.

## Validation included in source

V82 adds/extends:

- architecture and production-design static guardrails
- deterministic money/state-transition behaviour tests
- PostgreSQL tenant isolation checks
- a real concurrent document-counter test using 20 simultaneous database connections
- migration repeatability through the existing CI database job
- staging/local scale fixtures
- read-only k6 smoke/load scenario

Full `pnpm lint`, `pnpm typecheck`, production build, database integration and Playwright execution must still be run in an environment with the project dependencies/PostgreSQL/Chromium installed. V82 does not claim those runtime checks merely from static source inspection.
