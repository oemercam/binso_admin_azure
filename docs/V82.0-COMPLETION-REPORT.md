# V82.0 completion report

This report describes the implementation contained in the V82.0 source tree. It deliberately distinguishes implemented source changes from checks that require the normal pnpm/PostgreSQL/Playwright environment.

## PHASE 1 – SECURITY / TENANT

### Implemented

- Tenant-owned normalized rows use `organization_id` and PostgreSQL RLS.
- New child/source relationships use tenant-aware composite foreign keys where introduced.
- State API derives tenant context from authenticated membership and never accepts browser tenant identity as authority.
- Server-side relation validation covers customers, contacts, quotes, orders, contracts, time, invoices, payments, expenses, suppliers and credit notes.
- Invoice source time/expense relationships are verified server-side and duplicate billing sources are rejected.
- Existing canonical role/permission/entitlement architecture is preserved.
- Retry-safe state persistence supports idempotency keys.
- Document mail processing reads canonical normalized state after migration.

### Remaining

- Production PostgreSQL least-privilege role creation is an Azure/operator action. Application support exists through separate tenant/platform connection strings, but credentials/GRANTs cannot safely be invented from source code.
- A production backfill must be explicitly approved/run by an operator after dry-run review.

## PHASE 2 – DATABASE / NORMALIZATION

### Implemented

Normalized PostgreSQL persistence now covers customers, contacts, quotes/lines, contracts/lines, orders, time entries, invoices/lines, payments, employees, suppliers, supplier invoices, expenses, credit notes and customer activities. Stable external IDs preserve current UI IDs. Child document lines are synchronized transactionally. Legacy JSON no longer stores these arrays after successful normalized persistence/backfill.

### Remaining

- UI/workflow-only structures such as order policies, assignment rules, time evidence and app/document configuration still use their existing persistence paths. They were not mechanically moved because they have different ownership/lifecycle semantics.
- Existing `NOT VALID` tenant foreign keys should be validated in production only after the backfill and integrity review prove historical rows are clean.

## PHASE 3 – BUSINESS LOGIC

### Implemented

- Deterministic integer-minor-unit money calculations for quote/invoice/document totals.
- Server-side quote/order/invoice transition validation during persistence.
- Atomic PostgreSQL document numbering.
- Server-side relationship and financial invariant validation.
- Payment/credit totals checked against invoice value.
- Document sending uses server-authoritative normalized records.
- Advisory transaction locks + state revision conflict handling remain in place.

### Remaining

- BusinessStore still performs immediate optimistic UI orchestration before the server confirms persistence. The server is authoritative for accepted persistence, but a later strangler phase can move individual command handlers to dedicated server use-cases and return authoritative DTOs immediately.

## PHASE 4 – PERFORMANCE

### Implemented

- Bounded server list repository and `/api/business/records` pagination/search endpoint (default 50, maximum 100).
- Tenant/status/date/customer/order indexes aligned with list/query patterns.
- Scale fixture generator: 1,000 customers / 10,000 invoices / 100,000 time entries.
- Read-only k6 staging/local scenario.
- Client typography remains self-hosted by Next font output; no runtime Google CSS dependency.

### Remaining

- Existing UI pages have not all been converted to the paginated list endpoint. Full normalized collection hydration therefore remains a compatibility cost in the current strangler stage.
- No p50/p95/LCP/CLS/INP values are claimed until measured in staging with real dependencies and deployment infrastructure.

## PHASE 5 – SCALABILITY

### Implemented

- PostgreSQL-backed document counters and idempotency registry.
- PostgreSQL-backed distributed rate limiting already present and preserved.
- No new process-memory business-state authority introduced.
- Tenant and platform DB pools remain separate-capable.
- Concurrent document-counter integration test added.

### Remaining

- Azure Queue/Service Bus is not introduced merely for architecture optics. Existing mail outbox/internal jobs remain the durable pattern; infrastructure can be added when workload measurements justify it.

## PHASE 6 – MODULARITY

### Implemented

- Shared money, state-machine and pagination primitives.
- Dedicated normalized business persistence, list, document-counter, idempotency and backfill repositories.
- Server relation/integrity policies remain outside React UI components.
- Existing domain modules are preserved instead of mechanically reorganized.

### Remaining

- `business-store.tsx` is still intentionally large during the strangler migration. Splitting it before command-by-command server migration would create churn without removing responsibility.
- Legacy CSS remains as compatibility base, while typography ownership is now centralized. Further selector deletion should follow visual regression evidence, not blind line-count cleanup.

## PHASE 7 – PWA / UX

### Implemented

- V81.17+ safe areas, white PWA surface, sticky headers, native scroll ownership and mobile navigation are preserved.
- No `unsafe-eval` added to production CSP.
- Existing simplified navigation/product workflow remains unchanged.

### Remaining

- Runtime viewport/browser visual regression still requires Playwright in the normal dependency environment.

## PHASE 8 – TYPOGRAPHY / DESIGN SYSTEM

### Implemented

- Josefin Sans for brand/public headings.
- Inter for product UI, body, forms, navigation and tables.
- `next/font` build-time/self-hosted font delivery.
- Central tokens in `app/styles/tokens.css`.
- Canonical application/public type scales.
- Historical micro-text mapped toward 11–13 px readable roles.
- Tabular numerals on financial/data surfaces.

### Remaining

- Pixel-level visual sign-off should be performed after the normal Playwright/screenshots run because font metrics can change wrapping even when CSS checks are green.

## PHASE 9 – CI / TESTING

### Implemented

- V82 architecture check is part of GitHub Product checks.
- Existing static architecture/security/product checks remain compatible.
- Database test script includes normalized tenant RLS checks.
- Separate V82 concurrent numbering test runs under `test:integration:db`.
- V82 money/state tests run under unit tests.

### Remaining

- In the artifact-generation environment, project `node_modules`, pnpm, PostgreSQL and Playwright browsers were unavailable. Therefore full lint/typecheck/build/DB/E2E are intentionally not marked passed here. They must be executed locally/CI before commit/deploy.
